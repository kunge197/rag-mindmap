🧠 RAG 基本原理
❓ 为什么需要RAG
🎯 LLM 三大核心痛点
① 知识过时 — 训练数据有截止日期，新知识无法覆盖
② 幻觉问题 — 模型凭"记忆"编造，缺乏事实依据
③ 私域不可达 — 企业文档、个人数据模型训练时没见过
💡 RAG 解决方案
先检索外部知识库，再基于检索结果生成回答
= 把 闭卷考试 变成 开卷考试
可溯源 实时更新 低成本
📊 RAG vs 微调
RAG ✅ 实时更新

✅ 零训练成本
❌ 多一次检索延迟
微调 ✅ 响应更快
✅ 深度内化

🔍 检索 Retrieval
📄 ① 文档分块 (Chunking)
将长文档切分为语义完整的片段，是RAG的第一步也是最关键的一步
📋 分块策略详解（5种）
固定长度 按字符/token数切分
简单粗暴，易实现
语义分块 按句/段边界切分
保持语义完整
递归分块 递归拆分到目标大小
LangChain 默认策略
文档结构 按Markdown/HTML标题
利用天然层级
LLM分块 用LLM识别语义边界
最准确但成本高
⚠️ 常见问题与解决
❌ 语义断裂：一句话被切到两个块 → ✅ 使用块重叠(overlap) 10-20%
❌ 边界敏感：问题答案在不同块 → ✅ 适当增大chunk size
❌ 块大小选择：
小(128t)：精但碎片 中(512t)：平衡 大(1024t)：全但噪声
✅ 黄金法则：chunk_size 取决于文档类型 + LLM上下文窗口

🔬 查询向量化的多种方式
① 直接编码 — 用户原始问题直接用嵌入模型转向量
简单可能语义不精确

② 查询改写 (Query Rewrite) — LLM将问题改写后再编码
例："RAG怎么分块?" → "RAG系统中文档分块的技术方案和最佳实践"
召回率↑

③ 多视角查询 (Multi-Query) — 生成多个不同表述的问题
例：生成3-5个不同角度的查询，分别检索后合并结果
覆盖更全延迟↑

④ HyDE (假设文档编码) — 先让LLM生成一个假设答案
用假设答案去检索，因为答案比问题更接近目标文档的语义空间
零样本效果好依赖LLM质量

⑤ 查询分解 (Query Decomposition) — 复杂问题拆成子问题
例："RAG和微调的区别及各自适用场景"→ 拆成两个子查询分别检索
复合查询效果好

🎯 ④ 检索与召回策略
🔎 多种召回方式
● 稠密检索 — 语义相似度搜索 (ANN)
用向量距离(余弦/内积/L2)找最近邻

● 稀疏检索 — BM25 / SPLADE
关键词精确匹配，和稠密检索互补

● 混合检索 (Hybrid) — 稠密+稀疏融合
加权分数 = α×稠密分 + (1-α)×稀疏分
最佳效果

● 重排序 (Reranking) — 对粗召回结果精细打分
用Cross-Encoder模型逐对计算相关性
推荐：bge-reranker / Cohere Rerank
精度↑↑计算量↑

● MMR (最大边际相关性) — 多样性重排
避免召回结果太相似，保证信息多样性
推荐：Hybrid + Reranking
⚡ 增强 · ✍️ 生成
📝 增强 (Augmented)
Prompt 构建原则：
① 系统指令：定义角色和回答规则
② 检索上下文：按相关性排序的文档片段
③ 引用标注：标注信息来源 [来源1][来源2]
④ 用户问题：原始查询
⑤ 拒绝策略：上下文不相关时拒绝回答
💡 Prompt模板示例
你是一个AI助手，基于以下上下文回答问题。 如果上下文不足以回答问题，请明确说明。 上下文： [来源1] {{chunk_1}} [来源2] {{chunk_2}} 问题：{{user_query}} 请用中文回答，并在答案后标注来源编号。
✨ 增强进阶技巧
📌 上下文压缩
对检索结果进行压缩，只保留最相关信息
方法：LLM提取关键句 / 重排序截断 / 摘要化
节省token 减少噪声
📌 结果过滤与路由
● 相关性阈值：低于阈值不返回结果
● Agent路由：判断是否需要执行检索
→ 简单问候直接回答，复杂问题走RAG
● 多源路由：不同问题路由到不同知识库
→ 技术问题→技术库，政策问题→政策库
🤖 生成 (Generation)
LLM 基于上下文生成最终答案
⚙️ 生成质量控制
● 温度控制：知识问答设低温度(0.1~0.3)
● 幻觉检测：用LLM自我检查答案是否基于上下文
● 引用验证：每个论断对应到来源
● 流式输出：逐token返回，降低用户等待感
推荐模型：GPT-4o / Claude / DeepSeek / Qwen
🚀 进阶技巧
📝 查询改写 (Query Rewrite)
用户的原始问题往往口语化、简短，直接检索效果差
🔧 改写策略
① 去代词："它的原理是什么" → "RAG的原理是什么"
② 补充上下文："怎么分块" → "RAG中文档分块的方法"
③ 多角度扩写：生成3个不同表述并行检索
④ 翻译转写：中英混杂时统一语言
🔄 迭代检索 (Iterative)
一次检索不够？多次检索逐步深入
📋 多种模式
● 修正检索：生成失败→重新检索→再生成
● 多步推理：先检索引申知识，再查关键细节
● 递归检索：从小块开始→发现需要更大上下文→自动扩大
● Self-RAG：LLM自我判断是否需要检索，以及检索结果是否足够
🕸️ Graph RAG
微软提出的增强RAG：知识图谱 + 社区摘要
💡 核心差异
传统RAG：检索文档片段 → 语义相似
Graph RAG：提取实体关系 → 构建图谱 → 社区摘要 → 全局检索

优势：处理全局性问题(如"这个报告的总体结论是什么")
劣势：构建成本高，适合大规模文档集
💾 RAG缓存策略
● 语义缓存：相似问题直接复用结果
● KV Cache：高频文档预计算向量和Prompt
● 分层缓存：热数据在内存，冷数据在磁盘

⚠️ 常见误区与坏味道
🔴 误区清单
❌ Chunk太小或太大
太小：语义碎片；太大：噪声太多

❌ 忽略重排序
Top-K直接塞入，前排不相关内容污染LLM

❌ 不分文档类型都用同一种分块
代码、Markdown、PDF需要不同策略

❌ 不处理检索结果为空的情况
LLM在无相关信息时仍会尝试回答

❌ 忽略引用标注
无法追溯来源，等同于没做RAG

❌ 不使用混合检索
纯语义检索对专有名词/代码匹配差
🌟 最佳实践总结
✅ 根据文档类型选择分块策略 + 块重叠
✅ Hybrid Search (稠密+稀疏) + Reranking
✅ 查询改写提升召回率
✅ 低温度 + 引用标注 + 幻觉检测
✅ 设置拒绝策略：无相关信息时"不知道"
✅ 用 RAGAS/TruLens 持续评估优化
💡 推荐技术栈：LangChain + Milvus/Qdrant + bge + Hybrid Search + Reranker
